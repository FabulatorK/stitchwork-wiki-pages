B4 Texture2D (T2D) Sprites

intermediatecreator10 min read
For Stitchwork 0.9.0 · Last edited: 2026-10-19

Sprites · for creators.
Meet Texture2D (T2D), the trouble child of Silksong's art.
It does a bit of everything: menus, the HUD, effects, props, even some animation.
If a replacement will not take and the path looks right, T2D is usually behind it.

You'll be able to: recognize a T2D sprite, replace one individually, find the names you need, and avoid the one name collision (font atlases) that could garble text.

Before you start: B2 (the Graphics modes that find sprites).

What T2D is, and how to spot it

Silksong draws 2D art two ways (How Stitchwork Works explains why). tk2d is the orderly one: most animated characters, packed into shared atlases, with clips you can step through frame by frame. T2D is the trouble child. It is plain Unity Sprites and Texture2Ds, which the game hands straight to renderers and UI, and it turns up everywhere:

  • The HUD (health, silk, currency)
  • Menus and UI panels, prompts, icons
  • Many effects and ability visuals
  • Props that sit still in the scene
  • Some cinematic frames
  • Even the letters of the game's text (the font-atlas trap)

T2D animates too, and of course it does that its own way. tk2d has its own animation system; T2D borrows Unity's Animator. Each frame is a separate sprite that the Animator shows in turn. Replace the frames one file at a time, or replace their whole sheet (porting only). Stitchwork watches these sprites and applies your file each time its frame shows. The Animation mode does not list them, because it shows tk2d animation only.

The reliable tell is Graphics: a sprite that appears in the T2D Textures mode (and not in Animation) is T2D. When something refuses to apply, checking the other mode is the fastest diagnosis you have.

The folder is the routing

T2D paths carry a literal T2D/ segment. That's not decoration — it's how Stitchwork knows to route the file through the Texture2D system instead of tk2d. The same filename goes to a different pipeline under Sprites/{Coll}/... than under Sprites/T2D/....

The two paths

Individual sprite — replace one sprite within an atlas:

Sprites/T2D/{AtlasName}/{SpriteName}.png

Stitchwork builds a fresh Sprite from your PNG and sets it on every renderer (and UI Image) currently using that one. Good for a single icon, a HUD pip, one effect frame.

Sprites/T2D/Hornet/health_pip.png

Whole atlas — a porting-only path:

Spritesheets/T2D/{AtlasName}.png

This loads straight into the atlas texture in place, and it works — but we don't recommend authoring T2D art at the sheet level. A game update can repack a sheet and scramble your art; individual Sprites/T2D/ files key on the sprite and survive repacks. Use the sheet path to bring in existing sheet-based work (Porting Prior Work has the rules and the fine print), and prefer per-sprite files for anything new. The Atlas dump (the Dump row of the Preview panel) is still your friend — as a reference map of the sheet, not a template to ship.

Bigger canvas: size tags

A per-sprite T2D file can be bigger than the vanilla sprite. By default it draws at its own size: paint a 2× canvas and the sprite shows twice as big in the world. Two filename tags change that:

  • health_pip@e.png keeps the vanilla world size; the bigger canvas becomes extra detail instead.
  • health_pip@s2.5.png draws at exactly 2.5× the vanilla size, whatever the canvas (0.1 to 10).

The tag is stripped before matching, so both still replace health_pip. T2D files don't take the tk2d anchor tags (@t, @c, …).

Clean names

T2D atlases introduce themselves with their full Unity name: page, size, compression format and a hash, as in sactx-0-2048x2048-BC7-Hornet-abc123. You never type that. The clean name (Hornet here) is what goes in your path; Stitchwork strips the sactx-…- prefix and the trailing hash automatically, and T2D Textures shows you the clean name directly.

One name, several pages

Some clean names cover more than one atlas page: sactx-0-…-Hornet-… and sactx-1-…-Hornet-…. T2D Textures lists them as Hornet-0 and Hornet-1, each with its size. Pick texture in world helps here: the pick card shows the raw sactx-… name of the page under the cursor.

  • Per-sprite files need nothing extra. A file in Sprites/T2D/Hornet/ only goes to a page that has a sprite of that name. It never lands on a sibling page, or on another atlas, just because a name matches.
  • Whole-atlas files named Hornet.png go to the page whose size matches. When two pages share a size, the plain name can't tell them apart. Give the file the raw form with the page number — sactx-1-2048x2048-BC7-Hornet-abc123.png — and it goes to page 1 only. The page number, the format part (BC7 for most atlases) and the clean name have to be right; the hash at the end can be anything, even an old one. The size part of the name is not compared: the PNG's real pixel size must match the page. The raw names appear in the log's [T2D] lines.

Finding T2D names

All in Graphics (3), T2D Textures mode. The lists are in the Library panel (right); the previews are in the Preview panel (left). B2 › the T2D Textures mode has the steps: select a texture, read its sprites and the Preview readout, and check the S and number chips. For an effect that shows for only a few frames, use the T2D Log.

A name that you find there goes in a path with the T2D/ segment (the folder is the routing). Use the clean name (clean names).

And the same rule as everywhere: you can't find what isn't loaded. Go to the screen where the art appears, then look.

The edit loop

Select a sprite. Click Edit (new from vanilla) above the sprite list, or the small Edit on its row. Stitchwork writes the vanilla sprite to Sprites/T2D/<atlas>/<sprite>.png in your working folder and opens it in your image editor. After that, the button reads Edit (opens your file). The folder button beside it (tooltip "Open folder") opens the folder that holds your file. Paint, save, and hot reload shows it.

  • A sprite of a standalone texture lands in Sprites/T2D/_standalone/<TextureName>.png (see below).
  • A texture with no sprites (a particle texture, for example) has no sprite to choose. Edit (new from vanilla) then writes the whole texture to Spritesheets/T2D/<name>.png.
  • Your working folder ranks below every active pack. A pack's file for the same sprite wins, and a working-folder Sprites/T2D/ file does not show on an atlas page that an active pack replaces with a sheet.
  • White specks around the edges of your art come from white under the transparent pixels (Clip Studio Paint saves it). Clean sprite edges (CSP fix) in Settings › Rendering removes them when a file loads, for per-sprite files and for whole sheets (B1 has the details).

Dumping from the Preview panel

The Dump row of the Preview panel (Atlas, All sprites, Sprite) writes vanilla reference to Dumps/, which Stitchwork never loads. B2 › the T2D Textures mode has the steps, the status line and the Backdrop row. For T2D, use the Atlas dump as a reference map of the sheet. After a game update, delete the old dump before you dump again.

Flat files: no atlas folder

Sprites/T2D/{Sprite}.png (no atlas folder) also loads — it matches by bare sprite name across all atlases. Fine for unique names; the moment two atlases share a sprite name, qualify it with the atlas folder. The Pack Doctor marks flat files with an informational note for exactly this reason.

The third bucket: _standalone (mesh & material art)

Not everything 2D-looking is a sprite. Particle art is the texture of a particle system. Cloth banners that sway when you brush past them, grass and scrolling mist are plain mesh renderers whose material carries its own textures. Neither kind has a Sprite wrapper, and Stitchwork replaces both in place by texture. The dumper writes these to their own bucket:

Dumps/Sprites/T2D/_standalone/{TextureName}.png

The replacement path mirrors it, as always:

Sprites/T2D/_standalone/{TextureName}.png

This path rewrites the running texture's pixels in place, so it works no matter what kind of renderer is reading it. Keep your PNG at the exact dimensions of the dump — the in-place swap refuses size-mismatched files.

The trap: T2D can keep the same art in two shapes. The Crawcourt hanging rags are the canonical case — crawcourt_rags_0003_3 exists as a sprite inside the Crow atlas and as standalone material textures (crawcourt_rags_0003_3_textures + ..._base_textures). The cloth banner you see swaying in-game reads the standalone textures; the atlas sprite is a separate use. Replace the atlas copy and the banner doesn't change — the path was "correct," it just fed the wrong consumer.

The diagnosis rule: if a T2D replacement's path looks right but nothing changes in-game, search your Dumps/Sprites/T2D/_standalone/ folder for the same name (or the name plus a suffix like _textures). If it's there, that's the copy the object on screen is actually reading — replace that one instead. Some materials use a pair (a main texture and a _base_textures companion); replace both to start, then trim.

Effects that show up late

T2D does not always arrive on time. Stitchwork swaps T2D art on the objects in the room when the room loads, but some T2D art turns up later. Pooled effects, clones of objects that Stitchwork has seen, and sprite atlases that the game loads while it runs get your replacement when they arrive. Only an object that the game makes from nothing at that moment depends on a timed check.

A very short effect of that kind can come and go before the check sees it, and play once in vanilla. Two settings in the config's Performance section control the net, at a per-frame cost:

  • UninitCheckCacheRefreshSeconds (default 0.05) is how often the check looks. If busy rooms stutter, raise it to 0.30. An old config file keeps the old value 0.30: set 0.05, or delete the line while the game is closed.
  • ThoroughT2DEnrollment (default off) also enrolls objects that appear later without Stitchwork's hook, such as clones of some prefabs, late-loaded assets and objects that code builds. It's the heaviest option: turn it on only if you actually see an effect flash vanilla.

The font-atlas trap — name carefully

T2D even holds the letters. The game's text is rendered from font atlases, which are themselves Texture2Ds. If a pack ships a T2D PNG whose name collides with a font atlas — generic names like font.png are the classic offender — it could garble all system text into boxes.

Stitchwork hard-bans font atlases from replacement (it detects them and refuses the swap), so a pack can't do this by accident. The safe habit still costs nothing: name T2D files after the specific atlas you dumped, never generic catch-alls. If text shows boxes today, the usual cause is characters the game's font doesn't have — see Fonts.

When T2D won't cooperate

T2D is rarely broken. Usually, it is just somewhere else. Ask these questions in order:

  1. Is it T2D at all? Find the sprite in T2D Textures, not in Animation (how to spot it).
  2. Is the name right? Use the clean name. Add the atlas folder when two atlases share a sprite name (clean names).
  3. Is it the right page? A whole-atlas file goes to the page whose size matches (one name, several pages).
  4. Is there a second copy? Search Dumps/Sprites/T2D/_standalone/ for the same name. A _standalone file must keep the exact size of the dump (the third bucket).
  5. Did it arrive late? A very short effect can play once in vanilla before Stitchwork sees it (effects that show up late).
  6. Does a pack win? An active pack's file for the sprite, or its sheet for the page, wins over your working folder (the edit loop).

Individual or whole?

  • Individual when you're changing a handful of sprites, or want them isolated.
  • Whole atlas only to port existing sheet work (B3) — one PNG, matched to the original.

And they compose: a whole-sheet base with individual Sprites/T2D/ files layered on top, exactly as in B3. The same limit applies too: the stack holds inside one pack, and a higher pack's sheet hides a lower pack's individual files on that atlas page.
