面向代码模组的 API

参考创作者阅读约 5 分钟
适用于 Stitchwork 0.9.1 · 更新于: 2026-10-22

参考 · 面向模组作者
代码模组可以把游戏里发生的事告诉资源包。
模组发布一个“是/否”状态，资源包按名字引用它。
资源包创作者：怎样在 conditions.json 里引用模组的条件，请看资源包这一侧。

你将学会：从你的模组发布条件，在资源包的子集里引用它，以及在调用失败时读懂日志。

这套 API 现在能做什么

目前 API 只有一部分可用：条件。你的模组发布一个条件，也就是一个名字，加上一个返回 true 或 false 的函数。资源包在自己的某个子集（一个装着额外文件的文件夹）里引用这个条件。只要条件为 true，Stitchwork 就会显示这个子集。

比如，一个新增缚丝的模组发布了 BindActive。资源包就可以只在正在缚丝时显示一件发光的披风。资源包不用写代码，模组也不用准备美术资源。

子集目前还是预览功能（见条件激活）。API 的其他部分还没有做出来，见尚未实现。

约定

API 的每个版本都遵守下面这些规则：

  • 类是 Stitchwork.StitchworkApi，位于 Stitchwork.dll 中。它的完整名称永远不会改变。
  • StitchworkApi.ApiVersion 为 1。新版本只会添加成员。已有成员的签名和含义永远不会改变。破坏性的改动会使用新的成员名和新的版本号。
  • 参数只有字符串、布尔值和 Func<bool>。所以你的模组可以通过反射调用 API，不需要引用 Stitchwork 的类型。

ApiVersion 是常量，所以对硬引用了 Stitchwork 的模组来说，这个数字固定为编译时的值。要读取当前安装的版本，请通过反射读取这个字段：

typeof(StitchworkApi).GetField("ApiVersion").GetValue(null)

成员

这些成员都在 StitchworkApi.Conditions 里。

成员作用
bool ReadyStitchwork 已经启动时为 true。Stitchwork 处于停用状态时为 false，例如同时安装了 Patchwork 的时候。Stitchwork 启动之后，这个值在本次游戏期间不会改变。
bool Register(string owner, string name, Func<bool> predicate)发布条件 owner:name。用相同的 owner 和 name 再调用一次，会替换掉原来的判定函数（predicate）。
bool Unregister(string owner, string name)移除一个条件。引用它的资源包从下一次检查起读到 false。如果这个条件之前注册过，返回 true。
void Notify(string owner, string name)告诉 Stitchwork 值变了。Stitchwork 会在下一帧检查各个子集。
int RemoveAll(string owner)移除你的模组的所有条件。返回移除的数量。

参数要求：

  • owner 必须是你的模组的 BepInEx 插件 GUID。在插件类里，可以用 Info.Metadata.GUID 拿到它。GUID 不能包含 :。
  • name 只能包含字母、数字和 _。
  • predicate 不能为 null。

规则

  • 只在主线程上调用 API。从其他线程调用不会有任何效果，并返回 false。
  • 异常不会抛回你的模组。调用有误时，返回 false 或 0，或者什么都不返回，日志里会有一条警告。Stitchwork 尚未就绪时，调用返回 false，日志里什么都不会写。
  • 判定函数要快，而且不能有副作用。Stitchwork 每帧最多读取它一次。
  • 抛出异常的判定函数会被停用。日志里会有一行写明它的 owner。在你的模组再次调用 Register 之前，这个条件一直读作 false。
  • 模组停止时调用 RemoveAll，比如在 OnDestroy 里。BepInEx 无法卸载插件，所以你的模组要自己移除它的条件。

Stitchwork 什么时候读取值

只有当某个已启用的资源包里有子集引用了你的条件，Stitchwork 才会读取你的判定函数。这时它会在房间载入时、每隔 2 秒，以及 Notify 之后的下一帧读取判定函数。没有任何已启用资源包引用的条件，Stitchwork 永远不会读取。

所以值每次变化时，都调用一次 Notify。这个调用开销很小。

示例：硬引用

如果你的模组离不开 Stitchwork，就用这种写法。添加对 Stitchwork.dll 的引用。

using BepInEx;
using Stitchwork;

[BepInPlugin("example.bindmod", "Bind Mod", "1.0.0")]
[BepInDependency("Stitchwork")]
public sealed class BindMod : BaseUnityPlugin
{
    private bool _binding;

    private void Awake()
    {
        if (!StitchworkApi.Conditions.Ready) return;
        StitchworkApi.Conditions.Register(Info.Metadata.GUID, "BindActive", () => _binding);
    }

    private void OnBindChanged(bool on)
    {
        _binding = on;
        StitchworkApi.Conditions.Notify(Info.Metadata.GUID, "BindActive");
    }

    private void OnDestroy() => StitchworkApi.Conditions.RemoveAll(Info.Metadata.GUID);
}

[BepInDependency("Stitchwork")] 让 BepInEx 先启动 Stitchwork，再启动你的模组。所以在你的模组的 Awake 里，Ready 已经是 true。（Stitchwork 是 Stitchwork 的 BepInEx GUID。）

示例：反射

如果你的模组在没有 Stitchwork 时也必须能运行，就用这种写法。你的模组不需要引用 Stitchwork.dll。这种写法我们已经在游戏里运行过。上面那个硬引用的示例我们编译过，但没有在游戏里运行过。

using System;
using System.Reflection;
using BepInEx;

[BepInPlugin("example.softbindmod", "Soft Bind Mod", "1.0.0")]
[BepInDependency("Stitchwork", BepInDependency.DependencyFlags.SoftDependency)]
public sealed class SoftBindMod : BaseUnityPlugin
{
    private bool _binding;
    private MethodInfo _notify;

    private void Awake()
    {
        var conditions = Type.GetType("Stitchwork.StitchworkApi+Conditions, Stitchwork");
        if (conditions == null || !(bool)conditions.GetProperty("Ready").GetValue(null)) return;
        var register = conditions.GetMethod("Register", new[] { typeof(string), typeof(string), typeof(Func<bool>) });
        _notify = conditions.GetMethod("Notify", new[] { typeof(string), typeof(string) });
        register.Invoke(null, new object[] { Info.Metadata.GUID, "BindActive", (Func<bool>)(() => _binding) });
    }

    private void OnBindChanged(bool on)
    {
        _binding = on;
        _notify?.Invoke(null, new object[] { Info.Metadata.GUID, "BindActive" });
    }
}

装了 Stitchwork 时，软依赖同样会保持这个启动顺序，但不会让 Stitchwork 成为必需的前置。没有 Stitchwork 时，Type.GetType 返回 null，模组照常运行，只是没有这个条件。

资源包这一侧：模组条件

资源包用 owner:name 的格式引用模组的条件。owner 是模组的 BepInEx GUID，里面可以有点号和连字符。最后一个 : 后面的文字是名字。把它写进资源包的 conditions.json（和 pack.json 放在一起），有两种写法。

写成命名条件。子集再通过这个名字使用它：

{
  "conditions": { "BindActive": { "mod": "example.bindmod:BindActive" } },
  "sets": [
    { "name": "Bind", "when": "BindActive" }
  ]
}

直接写在子集的 when 里：

{
  "sets": [
    { "name": "Bind", "when": "example.bindmod:BindActive" }
  ]
}

子集的文件放在 Sets/Bind/ 里，结构和资源包一样：

MyPack/Stitchwork/
  Sprites/…              ← the pack's own files
  Sets/Bind/Sprites/…    ← only while the mod's BindActive is true

如果没有任何已安装的模组发布这个条件，它就读作 false。这样子集会保持关闭，资源包的其余部分不需要这个模组也能正常使用。

想知道某个模组的条件叫什么名字，请看它的 README，或者问它的作者。想看各个模组实际发布了哪些条件，就在 BepInEx/LogOutput.log 里搜索 registered the condition。

子集的完整格式，以及两个子集同时启用时会显示什么，请阅读条件激活。

日志

Stitchwork 会把下面这些行写进 BepInEx/LogOutput.log。同一种情况的警告，在一次游戏运行中只出现一次。

时机日志行
调用成功[StitchworkApi] <owner> registered the condition <owner>:<name>
owner 不合法[StitchworkApi] Register: the owner must be the caller's plugin GUID (got '<owner>').
name 不合法[StitchworkApi] Register: <owner> passed '<name>'; a condition name holds letters, digits and _ only.
判定函数为 null[StitchworkApi] Register: <owner> passed a null predicate for <name>.
不在主线程上[StitchworkApi] Register was called by <owner> off the main thread; it did nothing. Call it from Unity's main thread.
判定函数抛出异常（错误，每次注册只写一次）[RuleSets] the predicate '<owner>:<name>' of <owner> threw and is now off: <ExceptionType>: <message>
资源包引用了没有任何已安装模组发布的条件（警告，每个键只写一次）[RuleSets] no mod provides '<owner>:<name>'; it reads as false

Unregister 和 Notify 也会写出同样的警告，只是把 Register 换成它们自己的名字。

尚未实现

API 的下面这些部分已在计划中，还没有时间表。

  • 资源包与事件。模组将可以列出资源包，在本次游戏运行期间开启或关闭某个资源包或子集，并把这些改动一次性应用。事件会在重新加载完成时、以及子集变化时通知模组。这些部分还没有实现，形式也可能改变。
  • 实例皮肤。让单个对象拥有自己的皮肤，适用于 Architect 这样的模组。相关成员已经存在，但目前还不起作用：StitchworkApi.InstanceSkinsReady 为 false，ApplyInstanceSkin 返回 0，并在日志里写一条警告。你的模组可以在启动时检查 InstanceSkinsReady。
