问题自查

阅读约 15 分钟
适用于 Stitchwork 0.9.0 · 更新于: 2026-10-19

参考 · 面向所有人
有什么地方不对劲？来这里找找。
常见情况在前，少见情况在后。
页面最后会说明应该怎样提交一份有用的问题报告。

“我没看到任何变化 —— Stitchwork 压根没在运行”

把鼠标移到屏幕顶部边缘。如果资源包标签页滑了下来，说明 Stitchwork 正在运行。如果你关掉了顶部标签页，就改按 1。你也可以在 BepInEx/LogOutput.log 里搜索这一行：Stitchwork is loaded! Version: X.Y.Z (build …)。找不到这一行，就说明 Stitchwork 没有加载。

左下角的状态角标不适合拿来判断。它的眼睛图标可以把它收到屏幕左边缘外面，设置里的状态栏开关可以把它关掉；在场景内选取期间，以及 DebugMod 的面板显示时，它也会隐藏。

最常见的原因：你还装着旧模组 Patchwork。Stitchwork 会察觉到这一点，并在这次游戏期间关闭自己。主菜单右下角会有一条提示说明这件事，标题是 Stitchwork is off this session：

解决办法：从 BepInEx/plugins/ 中删除 Patchwork.dll。注意，Architect-Silksong 并不依赖 Patchwork，可以和 Stitchwork 正常共存——只有单独安装的 Patchwork 才会让 Stitchwork 进入停用模式。

其他原因：

  • 根本没装 BepInEx。Stitchwork 是 BepInEx 插件——没有 BepInEx 5，它就无法加载。检查游戏文件夹里有没有 BepInEx/core/BepInEx.dll。
  • Stitchwork 放错了位置。它的 DLL 必须放在 BepInEx/plugins/ 下一级的某个文件夹里（推荐命名为 StitchworkRoot/）。文件夹叫什么本身无所谓——Stitchwork 会根据 DLL 加载的位置找到自己——但 DLL 不能直接散放在 plugins/ 里，也不能藏在更深的子目录中。
  • 启动时出现了异常。打开 BepInEx/LogOutput.log，搜索 Stitchwork。插件 Awake 期间出现的错误会记在那里。

“启动后黑屏 —— 游戏一直进不了菜单”

如果日志开头附近有这些内容：

Invalid path in TextDataProvider : '…/StreamingAssets/aa/settings.json'
RuntimeData is null.  Please ensure you have built the correct Player Content.
InvalidKeyException: … No Location found for Key=Scenes/Pre_Menu_Intro

那么问题出在游戏本身的安装上，而不是 Stitchwork。丝之歌的所有内容都要通过 settings.json 这个资源目录来加载；它丢失或损坏时，游戏连自己的主菜单都加载不出来，只能一直停在黑屏上。出现这种情况，通常是因为游戏文件被直接修改或替换过（一些旧的换皮方法就是这么做的），或者安装文件损坏了。

修复方法：在 Steam 里右键点击游戏，依次选择属性 › 已安装文件 › 验证游戏文件的完整性。
然后移除所有直接替换游戏文件的模组。Stitchwork 从不碰 StreamingAssets/ 里的游戏资源文件本身 —— 它在内存里提供替换资源，也正因为如此，Steam 验证文件不会弄坏你的资源包。

“菜单自己左右乱跳——确认键还变成了取消”

就像有一只看不见的手，一直把菜单选项往左右拨；按确认却变成了取消；可每个设置界面都告诉你，按键绑定完全正确。绑定确实没问题——只是游戏同时在听两个手柄的输入，而其中一个可能是假的。

线索可以在 BepInEx/LogOutput.log 的开头附近找到：

Joystick connected ("Controller (XBOX 360 For Windows)").

如果你并没有 Xbox 手柄，这个设备就是虚拟的——它是你真实手柄经过转译后的“分身”。游戏会同时接收两者的输入：分身的摇杆没有回中，于是出现了凭空而来的左右输入；两者的按键布局不同（叉/圈与 A/B），于是确认和取消对调了。

你电脑上有某个东西创建了这个分身。常见的“嫌疑人”依次是：

  • 在游戏里初始化 Steamworks 的模组。 已确认的例子：SSMP（多人联机模组，0.3.1 及更早版本）——它启动时调用的 SteamAPI.Init() 会重新启用 Steam 的手柄转译，即使你已经为这个游戏关闭了 Steam 输入（问题已经反馈给模组作者）。删掉这个模组（或者先停用，等真要开房联机时再启用），分身就会消失。
  • 手柄转译软件——DS4Windows、reWASD、BetterJoy 这类软件，本来就是靠创建虚拟 Xbox 手柄来工作的。打开它们的“隐藏真实手柄”选项，或者直接关掉它们。
  • Steam 远程畅玩——连接进来的客户端会得到虚拟手柄，这些手柄只在游戏运行时存在，而且不受单个游戏的 Steam 输入设置约束。到 Steam › 设置 › 远程畅玩里检查已配对的设备。

不管是哪一种，验证方法都一样：找到原因 → 下次启动时日志里不再出现 Joystick connected 这一行 → 菜单恢复正常。

某个模组的 UI EventSystem

另一个完全不同的原因也会造成同样的症状，但日志里没有 Joystick connected 这一行——通常要从游戏中退回主菜单之后才会出现：某个模组的 UI EventSystem。模组可以为自己的窗口再创建一个 EventSystem。如果这个 EventSystem 在窗口关闭后仍然处于激活状态，它就可能操控游戏的菜单。如果你在用 Stitchwork 0.8.1，请更新：这个版本有这个问题。

要找出是哪个模组，就去日志里找 [ESWatch] 开头的行，它们一直开着。每次菜单的控制权发生变化，都会有一行写出当前掌握控制权的 EventSystem。如果是另一个 EventSystem 在操控菜单，下面的第二行就是警告：

[ESWatch] current '<path>' (<module>, navigation on|off) …
[ESWatch] '<path>' (…) is current with navigation on, not the game's EventSystem: a controller can act by itself in the menus.

警告里的那个名字就是原因所在。（[InputProbe] 行只在资源包面板打开时才会出现。）

在主菜单用过 Stitchwork 的窗口

第三种情况：在主菜单用过 Stitchwork 的窗口，同时还装了另一个自带窗口的模组（例如 UnityExplorer）。从 0.9.0 起，Stitchwork 的窗口关闭时，会把菜单交还给游戏。如果你用的是更早的版本，请更新。如果手柄还是会自己乱动，先别重启游戏。发送 BepInEx/LogOutput.log：每当菜单的控制权发生变化，日志里都会有一行 [ESWatch]。

“开着 UnityExplorer 时，没法在 Stitchwork 的输入框里打字”

默认情况下，UnityExplorer（或 CinematicUnityExplorer）的菜单显示时，Stitchwork 会主动让位：它的面板会关闭，它的按键也什么都打不开。Explorer 默认一启动就显示菜单。按 F7 把菜单隐藏，Stitchwork 就回来了。

想让两边同时开着，就到设置 › 常规里关掉为 UnityExplorer 让位（只有装了这两个模组之一时，这一项才会出现）。这样一来，Explorer 的菜单显示期间，Stitchwork 的文本框会显示光标，但不理会你的输入。把菜单隐藏（F7）后再输入，文本框就能正常使用了。

“日志里出现 Conflicting plugin detected: 'Customizer'”

如果日志里有 "Conflicting plugin detected: 'Customizer'"（或者其他 Customizer 附属模组），请把这些 DLL 从 BepInEx/plugins/ 中删除。它们和 Stitchwork 修改的是同一批精灵图钩子，两边会互相冲突（精灵图出错、敌人行为异常）。Stitchwork 能做同样的事，所以可以放心移除它们。其他需要移除的模组，见入门指南。

“我放进了一张精灵图 PNG，但什么都没变”

也就是常说的“精灵图替换没显示”——新手创作者问得最多的问题。

检查文件路径

路径很关键。常见的错误有：

  • 写成了 Sprite/，而不是 Sprites/——注意结尾的 s。可以相信Stitchwork自己生成的文件夹名。
  • 集合名称不对——不区分大小写，但必须和游戏里的集合一致。可以在图形 › 动画里核对准确的名称。
  • 材质名称不对——同上。
  • 精灵图名称不对——文件名（不含 .png）必须和精灵图名称一致。Idle_0.png 和 idle_0.png 都可以；idle 0.png（带空格）和 idle-0.png（带短横线）就不行。
  • 扩展名是大写的 .PNG——通常没问题，但在区分大小写的文件系统上会失效。保险起见，用小写的 .png。

文件监视器发现它了吗？

Stitchwork 支持热重载——文件改动会被检测到，片刻后就会生效。如果文件路径没错，游戏却没有读取它：

  • 试着切换一次场景（穿过一扇门）。载入场景时，所有替换都会无条件地重新应用一遍。
  • 在资源包管理器（资源包）里关掉这个资源包，点击应用。再打开这个资源包，然后再点一次应用。
  • 查看 BepInEx/LogOutput.log——在你保存文件的那个时间点附近，找 [Stitchwork] 开头的条目。你应该能看到一行和“reload”有关的日志。

那一帧现在在屏幕上吗？

如果角色正在播放动画，显示的是另一帧，你替换的图要等那一帧播放时才会出现。等对应的帧出现在屏幕上（待机、攻击到一半、某个特定表情）再看。

对于由 Animator 驱动、每帧都在变化的精灵图，每次显示那一帧时，都会应用一次替换。

短暂的特效还是原版美术？

有些特效只存在不到一秒，Stitchwork 可能会漏掉它们。打开 实用工具 › 探针 › 高级选项。在 扫描刷新间隔（秒） 下方，点击 默认 · 0.05。这会把 UninitCheckCacheRefreshSeconds 设为 0.05，也就是现在的默认值。旧版本保存的配置会保留原来的值 0.30。数值越低，越早发现短暂的特效。如果改完之后，东西多的房间开始卡顿，就把滑杆拖到更高的值，比如 0.30。改动会立即生效。

“我的美术边缘有白色斑点”

在游戏里，你的美术轮廓边缘有一圈细小的白色或浅色斑点。可在绘图软件里，同一张图看起来干干净净。

为什么会这样？ PNG 的每个像素都有颜色和透明度。完全透明的像素虽然看不见，但它仍然带着颜色。Clip Studio Paint 会把这个颜色误存成白色。游戏绘制你的美术时，会把每个边缘像素和它旁边的像素混合，让边缘看起来更平滑。混合时也会用到那些看不见的像素的颜色，于是藏起来的白色就混进了轮廓里：

美术的边缘像素旁边看不见的像素游戏里的边缘
深红色白色（Clip Studio Paint 存进去的）浅色斑点
深红色深红色（清理之后）深红色，没有斑点

游戏自带的美术没有这个问题。

那该怎么办？ 找到符合你情况的那一种：

  1. 如果你只玩游戏和使用皮肤， 那就什么都不用做。设置 › 渲染中的清理精灵图边缘（CSP 修复） 会在你的游戏里去掉这些斑点，而且默认开启。你的文件不会有任何改动。
  2. 你在制作资源包。 分享之前，先清理文件试试。点击体检按钮（资源包卡片上的听诊器图标）。如果报告发现了边缘偏浅的 PNG，资源包管理器会询问是否帮你清理这些文件。清理会把每个看不见的边缘像素，改成旁边美术的颜色。美术看起来和原来一样，而每位玩家都能看到干净的边缘，关掉了这项设置的玩家也不例外。Stitchwork 会先把每个要修改的文件复制到你工作区文件夹下的 Backups/clean-edges/以备份。详细说明请看资源包管理器。
  3. 你想在绘图软件里解决。 用选区工具（比如套索工具）只选中轮廓上出现斑点的那一段。然后对选区应用一次强度较低的高斯模糊。模糊会让轮廓在一两个像素内逐渐淡出。这样一来，游戏只会把藏起来的白色和几乎透明的像素混合，斑点就会变得非常淡。模糊也会让轮廓稍微变软，所以选区要小，强度要低。藏起来的白色仍然留在文件里：第 2 种做法的清理，才是彻底的解决办法。

“应用资源包时，游戏会停顿一下”

进度条走动期间，游戏会继续运行：Stitchwork 在帧与帧之间分成很多小步读取资源包图片，屏幕上正在显示的美术会最先载入。最后一步 正在收尾… 会重新载入音频、文本和字体，每帧处理一部分。这一步仍然可能让游戏短暂停顿。日志会写明是哪一部分慢，所以如果停顿得很久，请发送 LogOutput.log。

每次应用只会处理有变化的部分：文件没有变化的图集和音频会保持原样。

设置文件中 [Performance] 下的 SlicedReloadBudgetMs，决定应用过程每帧最多能占用多少时间（默认 12 毫秒）。数值越高，应用得越快，但应用期间的帧率也越低。

“应用资源包后，有些文字消失了或变成了乱码”

症状：应用了某个资源包之后，有些文字显示成方框（□□□）、乱码，或者干脆不见了。

  • 替换文本里出现方框（比如译文、生僻字，或者游戏从来不用的文字系统），说明游戏字体里没有这些字符。把一个包含这些字符的字体放进 Fonts/_fallback/；参见字体：修复缺字方框。一个全新的字符第一次出现时，可能会显示成方框，持续大约两秒；这是字形烘焙还没跟上，不是出错了。
  • 旧资源包里有名字像字体的 T2D 文件（font.png 之类），以前会让所有系统文字变成乱码。现在 Stitchwork 拒绝替换字体图集，所以这种情况不会再发生了；不过，按这类文件真正要替换的图集给它们重新命名，仍然是个好习惯。

如果还是看到乱码：

  1. 一次关掉一个资源包，每改一次都点击应用，找出是哪一个资源包出了问题。
  2. 提交 Bug 报告，写明资源包名称和你看到的现象（见下文的“提交有用的 Bug 报告”）。

“两个资源包改了同一个东西——谁会生效？”

优先级更高的那个。在资源包管理器里，资源包按优先级从上到下排列。调整优先级：在资源包管理器里把资源包卡片往上或往下拖。调整顺序之后，点击应用。

加了另一个资源包之后，原来的资源包不管用了。很可能是新资源包覆盖了相同的文件。被覆盖折叠栏会列出两个或更多资源包修改了同一项资源的地方，并告诉你哪个资源包盖过了哪个。左下角的状态角标会在数量大于零时显示“n 项被覆盖”——可以拿它粗略看看“我现在的配置有多乱”。

如果新资源包本来不该覆盖你那个资源包修改的内容，那就是新资源包的 Bug——它的文件命名有误，或者修改的范围比作者原本打算的更大。请把问题报告给那个资源包的作者。

“Stitchwork 的面板卡在了奇怪的位置”

双击面板的标题栏：面板就会回到它的默认位置。拖动没法把面板拖出屏幕，因为它总有一部分会留在画面里。贴着屏幕边缘卷起的面板不能移动：先把它展开。浮动面板卷成一根标题条后，仍然可以拖着标题条移动。

如果这样还不行，关掉游戏，编辑 BepInEx/config/Stitchwork.cfg 里的 [GUI] 部分：

  • 资源包面板：把 CanvasPMX 和 CanvasPMY 设为 0。
  • 开发中心的面板：把 DevHubPanels 清空。

如果面板里一片空白，或者界面不再响应，重启游戏之前先把日志复制出来，然后发送它——这种问题值得报告。面板丢失、点击没有传到面板上，或者 Stitchwork 出错时，它会自动把界面的快照写进日志。

“我的 Stitchwork 面板不见了”

  • DebugMod 的面板出现了。它们会关闭 Stitchwork 的面板。它们显示期间，Stitchwork 的按键什么都打不开，并且会有一条提示说明这一点。用 DebugMod 的切换键隐藏它的面板，然后再按一次标签页对应的按键。参见配套模组。
  • 另一个模组的菜单开着。遇到 Benchwarp 的菜单、FsmMaster 的叠加层、Architect 的编辑模式和 UnityExplorer 的菜单时，Stitchwork 也会用同样的方式让位。这时按 Stitchwork 的按键，会弹出一条提示，告诉你该怎么做。参见配套模组。
  • 你打开了另一个窗口。资源包、设置和开发中心的面板永远不会同时显示：打开其中一个，其他的就会关闭。资源包面板会保留你暂存的更改。
  • 点右键把它们卷起来了。卷起的面板会变成屏幕边缘的一根细条，上面显示着面板的名称。再点一次右键，或者点击这根细条，就能把它展开。
  • 在 Stitchwork 里，Esc 不会关闭或取消任何东西。Esc 归游戏使用，所以它会打开游戏的菜单。想在 Stitchwork 里取消，请点右键。

“替换的音频播错了/被截断/从头重播”

症状原因怎么办
一次性音效先播一次原版，之后才播你的替换启用资源包后，某个声音第一次触发时出现这种情况是正常的。Stitchwork 需要异步载入替换音频，而第一次触发时，载入还没完成。之后的触发都会使用已经缓存好的替换。不用做什么。如果第一次之后还是这样，请提交 Bug 报告。

“我的 anchors.txt 文件不起作用了”

anchors.txt 已经不再读取。Stitchwork 发现这个文件时，会记录一次警告。现在，锚点写在 PNG 文件名末尾的标签里：@t 顶部、@l 左侧、@r 右侧、@c 居中，不加标签（或者 @b）则是默认的底部。请按这个规则重新命名你的精灵图 PNG，然后删除 anchors.txt。完整的迁移步骤请看更大的画幅：锚点。

提交有用的 Bug 报告

一份有用的 Bug 报告包括：

  1. Stitchwork 版本。看资源包面板或设置的页脚（“Stitchwork X.Y.Z”），或者日志里的这一行：Stitchwork is loaded! Version: X.Y.Z (build …)。日志里的这一行还会写明具体是哪个构建。
  2. 你做了什么。写出导致 Bug 的具体步骤。“我打开游戏的时候它崩了”远不如“我读档之后走进灰沼时出的问题”有用。
  3. 你预期的结果，和实际发生了什么。
  4. 装了哪些其他模组。把它们列出来——尤其是会改动精灵图、音频或文本加载的模组。很多 Bug 都是模组之间相互影响造成的。
  5. 日志文件。如果 BepInEx/LogOutput.log 大小合适，就把它附上（太大的话先压缩成 zip）。没有日志，我们只能靠猜。要找到它，打开设置 › 高级选项，点击在文件夹中显示。BepInEx 文件夹会打开，在 Windows 和 macOS 上还会选中日志文件。每次启动游戏都会覆盖这个文件，所以重启之前先把它复制出来。
  6. 截图或短视频。画面方面的 Bug 尤其需要——“文字乱码了”配上一张截图，准确地展示乱码是什么样子，就清楚得多。

已知限制

当前版本的已知限制——有变通办法的都写在下面，正常使用时应该不会受到影响。

  • 同名的图集页，整图文件。如果一个 T2D 图集有好几页尺寸相同，只用通俗名命名的整图文件（Hornet.png）就分不清它们。请在文件名里加上页码——参见一个名字，多个图集页。单张精灵图的文件不受影响。
  • 启用大量资源包时，场景调色可能会短暂消失。可以复现的原因已经修复；但还有一种残留情况：启用了很多资源包的情况下，进入某些场景时，场景调色可能会暂时消失。重新进入这个场景——或者在资源包管理器里点击应用——就能恢复。
  • 增量垃圾回收（AutoEnableIncrementalGC）与“验证游戏文件的完整性”。Stitchwork 会（通过游戏的 boot.config）开启 Unity 的增量垃圾回收，让帧时间更稳定。如果你运行过 Steam 的验证游戏文件的完整性，boot.config 会被重置——Stitchwork 会检测到这一点，并在下次启动时重新应用这项设置（你会看到一条要求重启的提示）。不需要手动做任何事。
  • 只保留一份 Stitchwork.dll。BepInEx/plugins/ 下任何位置多出来的第二份拷贝——改过名的旧安装、一份备份、解压出来的发布文件夹——都会触发 BepInEx 的重复插件保护，让情况变得混乱。删掉多余的拷贝，只留一份。你自己的作品并不放在 DLL 旁边：它在工作区文件夹里，默认是 <Game folder>/Stitchwork/，总览面板会显示这个位置。参见Stitchwork 工作原理。
  • 与 Patchwork 共存。装着 Patchwork.dll 时，Stitchwork 会保持停用：参见入门指南。

这里没有列出的问题，请查看当前版本的更新说明，或者最新版本给出的社区频道。
